## 0. «Бот жив, но не отвечает» — найденные причины

| # | Причина | Где | Статус |
|---|---|---|---|
| 1 | Тяжёлые callback-обработчики (клик качества в Always Ask = вся загрузка + отправка, askf = извлечение форматов yt-dlp, cookie-download, gallery-dl fallback, img_range) выполнялись **на 8 потоках диспетчера Pyrogram** (`Client.executor`). 8 одновременных кликов — диспетчер занят целиком, бот не принимает ни одного апдейта, а процесс и systemd «живы». Ровно «после использования несколькими пользователями». | `always_ask_menu.py:2496`, `:1617`, `:3978`, `cookies_cmd.py`, `image_cmd.py` | ✅ |
| 2 | Синхронный `progress_bar` загрузки в Telegram Pyrogram тоже запускает в `Client.executor` — на **каждый чанк**, а внутри — правка сообщения и `time.sleep` на FloodWait до 61 с. Несколько параллельных отправок съедали те же 8 потоков. | `download_status.py:391`, `upload_guard.py` | ✅ |
| 3 | До перехода в фон на потоке диспетчера шли проверки `is_user_ignored/is_user_blocked/check_user`, каждая — **полная выгрузка списка из Firebase** (users ≈1.9k, blocked ≈3.5k записей) по REST; при деградации сети до ~90 с на вызов. | `firebase_init.py`, `decorators.py` | ✅ |
| 4 | ChannelGuard делал блокирующие запросы к БД **прямо на event loop** — во время скана весь бот стоял. | `channel_guard.py:183, 358, 363` | ✅ |
| 5 | Сетевые обрывы Telegram-сессий: туннель WARP (`wg-quick@wgcf`) перезапускается **~35 раз в сутки** — admin_phone_bot (CT102) по расписанию делает «Rotating IP on DE» каждые ~45 мин, плюс cron `0 */2 * * * restart wg-quick@wgcf`. Каждый рестарт рвёт все MTProto-соединения → reconnect-шторм; 02.11 09:17 — 45 переподключений и 0 обработанных апдейтов за 3 мин. | CT102 `admin_phone_bot.py:4782`, crontab CT108 | 🔧 |
| 6 | Watchdog «врал»: поток слал `WATCHDOG=1` каждые 30 с независимо от состояния бота (а в юните DE `WatchdogSec` вообще не включён). | `HELPERS/logger.py` | ✅ код / 🔧 юнит |

Что сделано в коде:

* все синхронные обработчики сообщений и callback'ов регистрируются через
  `install_handler_offload()` — диспетчер только ставит задачу в очередь и сразу
  свободен; лёгкие (меню, настройки) идут в пул `light` (16–64 потока), тяжёлые
  (`@background_handler`) — в пул `bg` с лимитом; при перегрузке пользователь
  получает «высокая нагрузка», а не тишину. В логах `[HANDLER-QUEUED]` (с глубиной
  очереди) отделён от `[HANDLER-START]` — по логам видно реальное ожидание;
* синхронные progress-callback'и выполняются в отдельном пуле, тики сливаются
  (пропускаются, пока предыдущий не закончил), финальный тик гарантирован;
* фильтры `_has_args_state` / `_has_trim_state` — async (не ходят в executor);
* проверки пользователя — точечные lookup'ы по ключу во всех движках;
* ChannelGuard: запросы к БД через `asyncio.to_thread`;
* heartbeat отправляется только если event loop реально отвечает (≤20 с);
  в шаблоне юнита `WatchdogSec=180` — зависший loop systemd перезапустит сам.
* тест `tests/smoke/test_h_handler_offload.py` воспроизводит сценарий: 8 «загрузок»
  висят, диспетчер не блокируется, меню обрабатывается, перегрузка сообщается.

Что нужно на сервере (🔧, по согласованию):

1. **Убрать постоянную ротацию IP**: отключить расписание «rotate IP DE» в admin_phone_bot
   (или делать ротацию только по факту блокировки YouTube и не чаще раза в N часов) и
   cron `0 */2 * * * systemctl restart wg-quick@wgcf`. Каждая ротация = обрыв всех
   Telegram-сессий и загрузок.
2. **Развести трафик**: Telegram (MTProto) — напрямую, мимо WARP; через WARP — только
   скачивание (YouTube и пр.). Подсети Telegram: `149.154.160.0/20`, `91.108.4.0/22`,
   `91.108.8.0/22`, `91.108.12.0/22`, `91.108.16.0/22`, `91.108.56.0/22`,
   `95.161.64.0/20`, `185.76.151.0/24`, IPv6 `2001:67c:4e8::/48`, `2001:b28:f23d::/48`,
   `2001:b28:f23f::/48` (policy-routing исключение в wgcf). Тогда ротация IP для YouTube
   вообще не касается Telegram. (Если прямой доступ к Telegram с хоста ограничен —
   оставить Telegram на отдельном, *не ротируемом* туннеле.)
3. Включить в юните `WatchdogSec=180`, `NotifyAccess=main`, `TimeoutStopSec=35`
   (шаблон `_etc/systemd/system/tg-ytdlp-bot.service`).
4. `amnezia-wireguard.service` в CT108 в цикле рестартов (счётчик 1 234 003): ищет
   несуществующий контейнер `19b08fa9e340` каждые 5 с. Отключить/починить: это
   3.4 млн строк журнала за 6 дней и постоянные запуски `docker`.
5. Ночной cron-зоопарк: `pip install -U ffmpeg*` каждую ночь, `apt install ffmpeg`
   каждую ночь, перезапись `/etc/resolv.conf` каждую минуту, `rm bot.log` —
   заменить на logrotate и обновления по расписанию с откатом.

## 1. База данных — ✅ в этой ветке

Firebase больше не обязателен: `USE_FIREBASE = False` + `DB_ENGINE = "json" | "sqlite" | "postgres"`.
Подробно — `docs/DATABASE.md`.

* SQLite (локально, без настройки) и PostgreSQL (локально или на отдельной ВМ для
  нескольких ботов; TLS `verify-full`, SCRAM, опционально mTLS; скрипт
  `scripts/db/setup_postgres_server.sh`);
* та же структура дерева и семантика, что у Firebase (включая правило массивов и
  push-ID) — экспорт идентичен Firebase и импортируется обратно;
* `scripts/db_migrate.py` — перенос между любыми движками с `--verify`;
* SQL-движки всегда актуальны: нет выгрузки дампа раз в N часов и лимитов квоты;
  кэш, записанный одним ботом, сразу виден остальным;
* проверено на реальном дампе DE (752 006 листьев): импорт SQLite 5.1 с /
  PostgreSQL 3.3 с, обратное чтение побайтно совпадает с исходником; точечный
  запрос SQLite 0.03–0.06 мс, PostgreSQL по TLS 1.4–2.1 мс (против полной выгрузки
  списков из Firebase на каждое сообщение);
* попутно исправлена потеря данных в режиме `dump.json`: пользователи, записанные
  через `db.child()`, затирались следующей синхронизацией кэша.

## 2. Производительность и масштаб (⏭)

1. **Очередь задач вместо потоков в процессе**: загрузки — в персистентную очередь
   (таблица в PostgreSQL / Redis) + N воркер-процессов. Задачи переживают рестарт,
   честная очередь по пользователям (round-robin, лимит на пользователя), приоритеты
   (кэш-хит — мгновенно, плейлисты — ниже). Это же даёт горизонтальное масштабирование
   на несколько ВМ с общей PostgreSQL.
2. Лимиты по ресурсам, а не по числу потоков: ffmpeg-перекодирование ≤ числа ядер (4),
   скачивание — по сети, отправка в Telegram — `max_concurrent_transmissions`
   PyroTGFork + семафор; лимиты per-domain (YouTube отдельно), чтобы не ловить бан.
3. Каталог загрузок — отдельный том (200 ГБ) с квотой и уборкой по месту, а не
   по крону; при нехватке — отказ новых задач с сообщением, а не падение.
4. Кэш: TTL/LRU для `video_cache` (372 тыс. записей растут бесконечно), индекс
   по дате, периодическая проверка, что message_id в канале ещё существует.
5. Логи: убрать INFO-спам на каждое обращение (`SAFE_SEND_DEBUG`, `local-cache access`),
   структурированный JSON-лог, logrotate. Сейчас лог — главный потребитель IO.

## 3. Наблюдаемость (⏭)

1. `/metrics` (Prometheus): глубина очередей light/bg, время в очереди, лаг апдейтов
   (now − message.date), активные загрузки/отправки, stall-ы, задержка БД,
   переподключения Pyrogram. Алерты — в лог-канал Telegram.
2. **Синтетический e2e-пинг**: пользовательская сессия ChannelGuard раз в 5 мин шлёт
   боту `/ping` и ждёт ответ ≤ 30 с. Это единственная проверка, которая видит
   «жив, но не отвечает» снаружи; при провале — алерт и (опционально) рестарт.
3. Дашборд: состояние пулов и очередей, последние ошибки по доменам.
